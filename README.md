# Task TG

Telegram Mini App для команд, задач и идей. Реализованы инфраструктура,
Telegram-авторизация, команды с ролями и приглашениями, задачи и Kanban,
идеи с преобразованием в задачи и локальный агент-исполнитель с PR-процессом.

## Структура

- `apps/web` — Vue 3 + Vite, TypeScript, запросы к `/api`.
- `apps/api` — Fastify, Prisma 7 и PostgreSQL.
- `packages/shared` — общие типы API (импортируются как типы, без runtime-кода).

Monorepo использует npm workspaces и один корневой `package-lock.json`.
Требуются Node.js 22.12+ (ветка 22), npm 10+ и Docker Compose v2.

## Локальный запуск

1. Скопируйте `.env.example` в `.env` (`Copy-Item .env.example .env` в PowerShell).
2. Выполните `npm ci`.
3. Запустите PostgreSQL: `docker compose up -d --wait postgres`.
4. Сгенерируйте клиент: `npm run db:generate`.
5. Примените миграции: `npm run db:deploy`.
6. Запустите приложения: `npm run dev`.

Клиент: http://localhost:5173. API: http://127.0.0.1:3000/api/health.
Vite проксирует `/api` на локальный API, поэтому CORS для разработки не нужен.
`GET /api/health` проверяет процесс; `GET /api/ready` выполняет запрос к БД
и возвращает 503 при её недоступности. Ответ не содержит подробностей ошибки БД.

## Проверки

```sh
npm run db:generate
npm run lint
npm run typecheck
npm test
npm run build
```

Тесты API используют Fastify inject и подмену проверки БД. Они проверяют
health/readiness, отсутствие утечки деталей ошибки в ответ и освобождение
ресурсов, но не заменяют интеграционную проверку настоящего PostgreSQL.

Авторизация проверяется дополнительными тестами подписи, срока действия,
повторного использования initData, сессии, cookie, Origin и rate limit.
Интеграционный сценарий PostgreSQL запускается отдельно:

`npm run test:integration -w @task-tg/api`. Он требует мигрированную пустую БД
с точным именем `task_tg_auth_test` в `DATABASE_URL`; рабочая БД не подходит.
Он последовательно проверяет авторизацию и команды, включая гонки при
использовании приглашения и изменении членства.

Жизненный цикл запусков агента проверяется отдельно на пустой БД
`task_tg_agent_test`:

```sh
npm run db:deploy -w @task-tg/api   # с DATABASE_URL на task_tg_agent_test
npm run test:agent-integration -w @task-tg/api
```

После изменения Prisma-схемы: `npm run db:migrate -- --name description`.
Созданные миграции сохраняйте в репозитории; на сервере используйте
`npm run db:deploy`, а не `migrate dev` или `db push`.

## Запуск всего приложения в Docker

```sh
docker compose --profile app up --build -d --wait
```

Клиент доступен на http://localhost:8080. Nginx передаёт `/api/` в Fastify.
API применяет миграции перед запуском. PostgreSQL хранит данные в named volume.
`docker compose down` сохраняет данные; флаг `-v` удаляет volume и данные.
Не запускайте локальный API и контейнерный API на одном порту одновременно.

Это конфигурация для разработки и проверки сборки. Production hardening,
HTTPS, резервные копии и окончательная инструкция VPS-деплоя — этап 6.

Текущее развёртывание на VPS и команды управления описаны в
[docs/vps.md](docs/vps.md). HTTPS-конфигурация использует порты 80 и 8443;
порт 443 занят существующим сервисом и не используется этим проектом.

## Переменные окружения

Настройки читаются из корневого `.env`; он исключён из Git и Docker build context.
Существующие переменные процесса имеют приоритет над `.env`.

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Инициализация PostgreSQL |
| `POSTGRES_PORT` | Локальный порт БД, по умолчанию 5432 |
| `DATABASE_URL` | Соединение Prisma при локальном запуске |
| `API_HOST`, `API_PORT` | Локальный адрес API, по умолчанию 127.0.0.1:3000 |
| `LOG_LEVEL` | Уровень серверных логов |
| `AGENT_WORKER_TOKEN` | Серверный токен worker-а агента, 32–512 символов; без него запуск агента возвращает 503 |
| `TELEGRAM_BOT_TOKEN` | Только API: токен бота; без него вход возвращает 503, а уведомления о задачах не отправляются |
| `APP_ORIGIN` | Разрешённый origin для POST, без завершающего `/` |
| `COOKIE_SECURE` | `true` на HTTPS; `false` допустимо только для локальной разработки |
| `INIT_DATA_MAX_AGE_SECONDS` | Срок первичного входа по initData, по умолчанию 300 секунд |
| `SESSION_TTL_SECONDS` | Срок сессии, по умолчанию 7 дней |
| `PUBLIC_HOST` | HTTPS hostname в Compose, без схемы и порта |

При изменении локальных реквизитов/порта синхронно обновите `DATABASE_URL`.
В Compose URL формируется с хостом `postgres`; `API_HOST` внутри контейнера —
`0.0.0.0`. Спецсимволы в компонентах URL требуют percent-encoding;
для текущей Compose-конфигурации используйте URL-safe пароль.
Изменение POSTGRES-переменных не меняет реквизиты уже созданного volume.
В браузер не передавайте секреты: переменные `VITE_*` публичны.
Для Telegram потребуется HTTPS-домен и бот; токен будет храниться только на API.

## Telegram и сессия

Бот: [@task_finc_bot](https://t.me/task_finc_bot). Mini App открывается через
кнопку меню бота; обычная ссылка в браузере не содержит Telegram initData.
Подключён официальный SDK `https://telegram.org/js/telegram-web-app.js`.
Вне Telegram приложение предлагает открыть бота, без обхода авторизации.

- `POST /api/auth/telegram` принимает JSON `{ "initData": "..." }`.
- `GET /api/me` возвращает подтверждённого пользователя либо 401.
- `POST /api/auth/logout` удаляет текущую сессию и cookie.
- Публичны только health, ready, вход и выход; остальные маршруты защищены по умолчанию.
- Для POST обязателен `Origin`, равный `APP_ORIGIN` (включая порт).

API сверяет HMAC-SHA256 с bot token, проверяет auth_date, дубликаты параметров
и данные пользователя. Повторное использование одного initData блокируется
уникальной записью внутри транзакции вместе с созданием сессии.
При потере ответа после входа или после выхода закройте Mini App и откройте заново,
чтобы получить свежие initData. Сначала клиент пробует восстановить имеющуюся сессию.

Сессия — случайный токен, в БД хранится только SHA-256. На VPS cookie имеет
HttpOnly, Secure, SameSite=None, Partitioned и префикс __Host-. Токен сессии
не возвращается в JSON и не записывается в localStorage. Поддержка cookie
конкретным Telegram webview проверяется повторным запросом `/me` после входа.
Проверка Origin защищает изменяющие запросы при SameSite=None.
Ограничение попыток входа пока общее для Nginx-прокси: 20 в минуту;
перед масштабированием следует настроить доверенные адреса прокси и лимиты по клиенту.

## Команды и приглашения

После входа можно создать команду или вступить в существующую. Команда
содержит название (1–80 символов), описание (до 500 символов) и участников.
Список команд и сведения о каждой доступны только её членам; для постороннего
возвращается 404 без подтверждения существования команды.

| Действие | Владелец | Администратор | Участник |
| --- | --- | --- | --- |
| Просмотр команды и участников | Да | Да | Да |
| Изменение названия и описания | Да | Да | Нет |
| Создание и отзыв приглашений | Да | Да | Нет |
| Изменение ролей других участников | Да | Нет | Нет |
| Исключение участников | Всех, кроме владельца | Только обычных участников | Нет |
| Удаление команды | Да | Нет | Нет |
| Выход из команды | Нет | Да | Да |

У команды один владелец. В MVP передача владения не реализована;
владелец может удалить команду с подтверждением её названия в интерфейсе.
Удаление команды удаляет её членство и приглашения в одной транзакции.

Приглашения одноразовые, действуют 24 часа, содержат 256 случайных битов.
В БД сохраняется только SHA-256; исходный код отображается один раз после создания.
Одновременно доступно до 20 активных приглашений. Понижение роли, исключение
или выход администратора отзывает его неиспользованные приглашения.
Повторное повышение роли не восстанавливает эти приглашения.

Для прямых приглашений пользователь включил Main Mini App в BotFather.
Ссылка имеет вид `https://t.me/task_finc_bot?startapp=join_<code>`.
Код из start_param заполняет форму, вступление требует нажатия кнопки.
Также можно открыть приложение через меню бота и вставить код вручную.
Код передаётся в JSON-теле POST, Nginx не записывает query-параметры в access log.

API:

- `GET/POST /api/teams` — список своих команд и создание.
- `GET/PATCH/DELETE /api/teams/:teamId` — просмотр, редактирование и удаление.
- `POST /api/teams/:teamId/leave` — выход.
- `PATCH/DELETE /api/teams/:teamId/members/:userId` — роль и исключение.
- `GET/POST /api/teams/:teamId/invites` — журнал и создание приглашений.
- `DELETE /api/teams/:teamId/invites/:inviteId` — отзыв.
- `POST /api/teams/join` с `{ "token": "<code>" }` — вступление.

Изменяющие запросы требуют Origin и действующую сессию. Права читаются из БД
при каждом действии, а не из cookie. Операции одной команды блокируют её строку
в PostgreSQL, чтобы вступление, отзыв, исключение и изменение ролей не обходили
проверки при одновременных запросах.

## Задачи (этап 4)

Участники команды всех трёх ролей могут просматривать, создавать, изменять
и удалять её задачи. Постороннему возвращается 404. Ответственный — только
текущий участник этой команды либо `null`. При выходе или исключении участника
назначения снимаются, версии затронутых задач увеличиваются; авторство сохраняется.

- `GET/POST /api/teams/:teamId/tasks` — список и создание.
- `GET/PATCH/DELETE /api/teams/:teamId/tasks/:id` — отдельная задача.
- Поля: `title` (1–160), `description` (до 5000), `status`
  (`TODO`, `IN_PROGRESS`, `DONE`), `assigneeId` (UUID либо `null`).
- `PATCH` требует `version` и хотя бы одно изменяемое поле.
  `DELETE` принимает JSON `{ "version": 1 }`.
- Старая версия возвращает 409 `VERSION_CONFLICT`. Запись не меняется.
- Фильтры списка: `q`, `status`, `assignee` (UUID, `me`, `unassigned`).
  Страница — до 50 записей; следующий запрос передаёт `cursor=nextCursor`.
  Курсор из другой команды или удалённой задачи возвращает 400 `INVALID_CURSOR`.

Внутри команды доступна Kanban-доска. Статус меняется в форме задачи;
перетаскивание не реализовано. Форма открывается как bottom sheet на узком экране
и диалог на широком. При конфликте и сетевом сбое введённые поля остаются в форме.
Для конфликта доступны загрузка текущей записи, сравнение и явный выбор:
сохранить свой ввод для повторной отправки или принять поля сервера.
Фильтры применяются кнопкой; при изменении фильтра курсор сбрасывается.

После создания задачи или первого преобразования идеи в задачу API отправляет
уведомление в Telegram всем участникам команды, кроме автора действия.
Сообщение содержит команду, название, описание (до 400 символов), автора и
ответственного. Отправка best-effort: недоступный получатель (бот не запущен
или заблокирован) не отменяет создание задачи; ошибки попадают в лог API без
текста токена. Отправка выполняется после успешной записи в БД и не повторяется
при повторном запросе преобразования. Пользователь должен хотя бы раз открыть
бота, иначе Telegram не позволит боту написать ему первым.

## Идеи (этап 5)

В разделе команды доступен список идей, поиск по названию/описанию, дозагрузка,
форма создания/редактирования и удаление с подтверждением. Все три роли участников
могут работать с идеями своей команды. Для постороннего возвращается 404.

- `GET/POST /api/teams/:teamId/ideas` — список и создание.
- `GET/PATCH/DELETE /api/teams/:teamId/ideas/:id` — отдельная идея.
- Поля: `title` (1–160), `description` (до 5000).
- `PATCH` принимает `version` и хотя бы одно поле; неуказанные поля сохраняются.
- `DELETE` принимает JSON `{ "version": 1 }`. Старая версия — 409 `VERSION_CONFLICT`.
- Список: `q`, `cursor`; до 50 записей и `nextCursor`, курсор проверяется на команду.
- `POST /api/teams/:teamId/ideas/:id/convert` с `{ "version": 1 }` возвращает
  `{ "idea": ..., "task": ... }`. Создаётся задача TODO без ответственного,
  с сохранёнными названием/описанием идеи; автор задачи — преобразующий участник.

Создание задачи и отметка преобразования выполняются в одной транзакции с блокировкой
команды. Одновременные и повторные запросы возвращают одну и ту же задачу, включая
повтор со старой версией уже преобразованной идеи. Если до преобразования идея
изменилась, требуется актуальная версия. После преобразования идея остаётся
для чтения: PATCH возвращает 409 `IDEA_CONVERTED`. Изменения выполняются в задаче.
Удаление идеи оставляет задачу; удаление задачи обнуляет связь идеи и повторное
преобразование возвращает 409 `CONVERTED_TASK_DELETED`, не создавая дубликат.

Перед преобразованием UI требует сохранить локальные изменения. После успеха
Kanban обновляется. Конфликт и сетевой сбой сохраняют ввод. При чужом преобразовании
несохранённый текст остаётся доступен для копирования; доступны загрузка и сравнение
актуальных данных. Это сохранение внутри открытой формы, не восстановление после
перезагрузки страницы. Проверка внутри реального Telegram webview пока не выполнена.

## Агент-исполнитель

В редакторе существующей задачи доступна кнопка **«Отправить агенту»**.
Любой участник команды может поставить задачу в очередь и отменить активный
запуск. Агент работает на компьютере, где запущен worker, в отдельном git
worktree и отдельной ветке. Он оценивает задачу, составляет план, вносит
изменения, запускает проверки, коммитит результат и открывает pull request.
Автоматического слияния нет: PR проверяет человек.

В карточке задачи также есть диалог с агентом. Сообщение пользователя
создаёт новый запуск и передаётся агенту вместе с последними сообщениями.
Агент может задать вопрос через `NEEDS_INPUT`; ответ пользователя создаёт
следующий запуск с историей. Чат не даёт агенту доступа к деплою, merge,
SSH или production-shell: эти действия остаются отдельными и требуют
подтверждения.

### Проекты задач

У каждой новой задачи и идеи есть проект: `TG_BUDGET` (`tg-budget`, учёт
финансов) или `TASK_TG` (этот таск-менеджер). В интерфейсе первым и по
умолчанию выбран `tg-budget`. Проект виден на карточках и в редакторе; от
него зависит, в каком репозитории worker создаст worktree и PR. Старые
записи без проекта остаются доступными для чтения, но их нужно назначить
вручную перед отправкой агенту или преобразованием идеи в задачу.

### Этапы запуска

`QUEUED → ASSESSING → PLANNED → WORKING → REVIEW → DONE`.
Возможны `FAILED`, `CANCELLED` и `NEEDS_INPUT`. При создании запуска задача
переходит в `IN_PROGRESS` и остаётся в этом статусе после PR до проверки
человеком. Этапы и журнал видны в редакторе задачи; активный запуск
обновляется опросом каждые 4 секунды.

### Настройка API

Добавьте в корневой `.env` (только сервер) случайный токен не короче 32 символов:

```dotenv
AGENT_WORKER_TOKEN=replace-with-at-least-32-random-characters
```

Без этого токена создание запуска возвращает `503 AGENT_NOT_CONFIGURED`.
Токен должен совпадать с `AGENT_WORKER_TOKEN` в окружении worker.

### Настройка worker

Worker — это отдельный локальный процесс. Ему нужны Node.js 22.12+, Git,
установленный OpenCode CLI, авторизованный GitHub CLI (`gh auth login`) и
доступный API. Скопируйте шаблон и заполните значения:

```powershell
Copy-Item scripts/agent-worker.env.example .agent-worker.env
```

Минимально важны:

| Переменная | Назначение |
| --- | --- |
| `AGENT_API_URL` | URL API, например `http://127.0.0.1:3000` |
| `AGENT_WORKER_TOKEN` | тот же токен, что в `.env` API |
| `AGENT_REPO_DIR_TASK_TG` | путь к клону этого репозитория (fallback — `AGENT_REPO_DIR`) |
| `AGENT_REPO_DIR_TG_BUDGET` | путь к клону `rozhokserega-lang/tg-budget` |
| `AGENT_BASE_BRANCH` | база для worktree, по умолчанию `main` |
| `AGENT_OPENCODE_BIN` | путь к `opencode-cli.exe` |
| `AGENT_MODEL` | необязательная модель `provider/model` |
| `AGENT_INSTALL` | `true` — выполнять `npm ci` и `db:generate` в worktree task-tg |
| `AGENT_INSTALL_TG_BUDGET` | `false` — tg-budget статический, npm-установка не нужна |
| `AGENT_PUSH` | `true` — отправлять ветку в `origin` |
| `AGENT_PR` | `true` — создавать pull request через `gh` |
| `AGENT_ONCE` | `true` — взять один запуск и выйти |
| `AGENT_APP_URL` | необязательная ссылка на приложение в PR |

`.agent-worker.env` и `.agent-worktrees/` исключены из Git.
Запуск из корня репозитория:

```powershell
npm run agent:worker
```

Или напрямую: `node scripts/agent-worker.mjs`. После запуска worker опрашивает
API, забирает `QUEUED`-запуски и обрабатывает их по одному. Остановка worker
по Ctrl+C не отменяет уже начатый запуск; отмена доступна в интерфейсе задачи.
Если worker перестал присылать heartbeat, аренда запуска истекает через
180 секунд. Следующий claim помечает такой запуск `FAILED` с `LEASE_EXPIRED`;
до этого запуск можно отменить в интерфейсе, а worktree остаётся для разбора.

### Что выполняет worker

1. Выбирает репозиторий по `run.project`: `AGENT_REPO_DIR_TG_BUDGET` или
   `AGENT_REPO_DIR_TASK_TG`. Запуск без проекта отклоняется worker-ом.
2. Создаёт worktree от `AGENT_BASE_BRANCH` с веткой `agent/<run>-<task>`.
3. Для task-tg при `AGENT_INSTALL=true` выполняет `npm ci` и
   `npm run db:generate` с очищенным окружением без production-секретов.
   Для tg-budget установка пропускается (`AGENT_INSTALL_TG_BUDGET=false`).
4. Запускает OpenCode с агентом `task-agent` из `.opencode/agents/task-agent.md`
   и передаёт задачу вместе с последними сообщениями чата как недоверенный
   контекст. Для tg-budget worker временно создаёт такой файл с разрешениями
   только на `node`/read-only `git` и удаляет его до коммита. Агенту доступны
   только чтение/правка файлов worktree, разрешённые команды проекта и helper
   `scripts/agent-report.mjs` (в task-tg); сеть, subagents, skills, `.env`,
   `.git`, `package.json` и lockfile закрыты.
5. После агента сканирует staged-файлы на lease-токен, GitHub-токены и
   приватные ключи, блокирует правки защищённых файлов и запускает проверки
   проекта в очищенном окружении: `test/lint/typecheck/build` для task-tg,
   `node --test`/`node --check`/`git diff --cached --check` для tg-budget.
6. Коммитит изменения, при `AGENT_PUSH=true` отправляет ветку и при
   `AGENT_PR=true` открывает PR (черновик, если проверки не прошли или
   OpenCode завершился с ошибкой).
7. Завершает запуск статусом `DONE`/`FAILED`, сохраняет ветку, PR и summary.
   Ненулевой код выхода OpenCode помечает запуск `FAILED`, даже если
   проверки прошли; ветка и PR остаются для ручного разбора.

### Чат по задаче

В карточке задачи есть диалог с агентом. Сообщение сохраняется в
`AgentMessage` и создаёт новый запуск; worker получает последние сообщения
как недоверенный контекст. Если агент вызывает
`node scripts/agent-report.mjs needs_input "вопрос"`, вопрос появляется в
диалоге, а следующий ответ пользователя создаёт новый запуск с историей.
После завершения запуска в диалог добавляется summary или ошибка. Каждое
сообщение — отдельный worktree и запуск; незакоммиченные изменения при
`NEEDS_INPUT` не сохраняются. Деплой и merge из чата не выполняются.
Миграция: `20261028120000_agent_messages`.

Агент не является жёсткой песочницей: тесты и сборка — это выполняемый код,
поэтому они могут обращаться к файлам пользователя и сети. Текст задачи и
сообщения чата считаются недоверенными; worker не передаёт агенту
`AGENT_WORKER_TOKEN`, Telegram-токен и production `DATABASE_URL`. Всё равно
проверяйте diff и PR: остаточный риск prompt injection и вредоносного кода
в тестах сохраняется.



## Интеграция и следующий этап

`npm run test:integration -w @task-tg/api` последовательно запускает auth,
teams, tasks и ideas на отдельной `task_tg_auth_test`. Не запускать на рабочей БД.
Проверяются права и изоляция, валидация и версии, поиск и страницы, назначения
при выходе/исключении, гонки CRUD и преобразования, повторы без дубликатов,
удаление связанной задачи, откат транзакции и каскадное удаление команды.

production hardening и итоговая документация. Часть этапа 6 выполнена;
